# Farn Design System — Full Review Report
**Date:** 2026-06-04  
**Scope:** Post T-15 (IA restructure) · T-35 (accordion) · T-44 (component group consolidation)  
**Method:** 6 independent agent reviews across orthogonal perspectives

---

## Executive Summary

Farn has crossed a meaningful threshold. The three-pillar IA is clean, the token architecture is solid, and 9 components are shipped and well-documented. The restructuring work is complete and coherent. However, the system is **not yet v1.0-ready**: 5 critical bugs in shipped components, 5 sections of CLAUDE.md that will cause agents to do the wrong thing, and a component inventory that covers roughly 40% of what a production UI needs.

**Overall grade: B / solid beta**

| Dimension | Grade | Primary issue |
|---|---|---|
| Token architecture | A− | Hardcoded RGBA values; missing `--color-on-success/warning` |
| Component quality | B− | Missing `:focus-visible` on buttons (WCAG fail); badge tokenization incomplete |

| Consumer DX | C+ | Import chain unclear; Tier-3 override pattern undocumented; no llms.txt |
| CLAUDE.md accuracy | D+ | 5 critical instructions that will cause agents to fail |

## Perspective 1 — Token System

### Passed

- Naming conventions: all `--in*`, `--bm*`, `--fo*`, `--bl*`, `--color-*`, `--space-*` etc. follow convention; no legacy names
- Dark/light semantic coverage: 21 semantic tokens each side, fully symmetric
- Surface model: `base/layer/overlay` correctly defined for both themes with dual selector patterns
- Build artifact: `dist/farn-tokens.css` concat order and content verified correct
- Spacing scale: complete and proportional (`--space-xs` through `--space-4xl`)
- Motion tokens: 5 durations + 3 easings — sufficient for all shipped patterns
- Typography enforcement: `font-variation-settings: 'opsz'` present on all Fraunces usages in token/typography-classes layer

### Issues

**CRITICAL — Hardcoded RGBA values in `tokens/dark-light.css`**  
Four values embed palette color as raw hex-derived RGB integers, breaking the single-source-of-truth principle:

| Line | Token | Hardcoded | Should reference |
|---|---|---|---|
| 30 | `--color-border-subtle` (light) | `rgba(55,65,81,0.12)` | `--in1-iron` (rgb 55,65,81) |
| 31 | `--color-ghost-border` (light) | `rgba(55,65,81,0.25)` | `--in1-iron` |
| 64 | `--color-border-subtle` (dark) | `rgba(75,85,99,0.25)` | `--in2-slate` (rgb 75,85,99) |
| 65 | `--color-ghost-border` (dark) | `rgba(247,246,243,0.25)` | `--bm2-birch` (rgb 247,246,243) |

**Fix:** Replace with `color-mix()`:
```css
--color-border-subtle: color-mix(in srgb, var(--in1-iron) 12%, transparent);
--color-ghost-border:  color-mix(in srgb, var(--in1-iron) 25%, transparent);
```
`color-mix()` has broad support (Chrome 111+, Firefox 113+, Safari 16.4+) and is already used in `--input-focus-shadow`.

**MAJOR — Missing `--color-on-success` and `--color-on-warning`**  
`--color-on-error` exists (maps to `--bm2-birch` in both themes) but the success and warning equivalents are absent. Alert variants that need light text on colored backgrounds are forced to hardcode `--bm2-birch` or use `--color-accent-text` — both are semantic mismatches.

**MAJOR — Badges lack Tier-3 token coverage**  
Every shipped component exposes Tier-3 overrides except badges. Badge fills reference palette tokens directly in component-classes.css (lines 16–22):
```css
.badge-published { background: var(--bl3-moss); color: var(--color-accent-text); }
```
Consumers cannot retheme a single badge variant without overriding the CSS class. The following tokens are missing from `tokens/components.css`:
- `--badge-height` (currently hardcoded `22px`)
- `--badge-padding` (currently `0 8px`)
- `--badge-letter-spacing` (currently `0.04em`)
- `--badge-{general,published,draft,archived,beta,research,category}-bg`
- `--badge-{variant}-text` (most variants use `--color-accent-text` — semantically wrong for Bloom-backed fills)

**MINOR — Shadow token value contains magic numbers**  
`--overlap-card-shadow-raised` is a token, but its value is `0 -4px 32px rgba(0, 0, 0, 0.14)` — an opaque definition that can't be theme-overridden semantically.

| Form fields | input, textarea, select + wrapper/hint | hover, focus, disabled, error | Yes |

### Critical accessibility issues

**CRITICAL — Buttons have no `:focus-visible` in `farn-components.css`**  
The button's focus state relies on the global outline rule in `base.css` (shipped in `farn.css`). When a consumer loads only `farn-components.css` — the documented standalone use case — keyboard focus on buttons is invisible. This is a WCAG 2.1 Level A failure (Success Criterion 2.4.7 Focus Visible).

`component-classes.css` line 57–58 handles hover and active, but has no focus rule. `card-interactive` (line 190) explicitly adds its own `:focus-visible` rule with the correct comment "explicit here for farn-components.css standalone use" — buttons need the same treatment.

**Fix:**
```css
.btn:focus-visible {
  outline: 2px solid var(--color-accent);
  outline-offset: 3px;
}
```

**CRITICAL — Breadcrumb links have no `:focus-visible`**  
`component-classes.css` lines 355–358 handle `:hover` and `[aria-current="page"]` only. Keyboard users traversing a breadcrumb cannot see the focused item.

**Fix:**
```css
.breadcrumb-item a:hover,
.breadcrumb-item a[aria-current="page"],
.breadcrumb-item a:focus-visible {
  color: var(--color-text);
}
```

### Major CSS quality issues

**MAJOR — `color-mix()` in input focus shadow has no fallback**  
`tokens/components.css` line 81:
```css
--input-focus-shadow: 0 0 0 3px color-mix(in srgb, var(--color-accent) 15%, transparent);
```
In browsers < Chrome 111 / Firefox 113 / Safari 16.4, the property resolves to invalid and input focus has no glow. No `@supports` fallback exists. Given that `color-mix()` is also used to fix the hardcoded-RGBA issue above, this is a consistent gap.

**MAJOR — Button gap and padding are magic numbers**  
`component-classes.css` line 30: `gap: 6px` and line 32: `padding: 0 16px` — neither maps to the spacing scale and neither has a token. Add `--btn-gap` and `--btn-padding-x` to `tokens/components.css`.

**MAJOR — Form inputs use `:focus` instead of `:focus-visible`**  
`component-classes.css` line 106 applies visual focus styles on all focus, including programmatic focus from JavaScript. The modern pattern is to use `:focus-visible` for the visual indicator (keyboard/sequential), pair with `:focus { outline: none; }` to suppress browser defaults, and preserve the box-shadow indicator for `:focus-visible` only.

**MAJOR — Section dividers invisible when JS is disabled**  
`.section-wave` and `.overlap-card` start at `opacity: 0` and only become visible when scroll-reveal.js adds `.is-visible`. If JavaScript is disabled or blocked, these elements are permanently invisible — a progressive enhancement failure.

**MINOR — Accordion toggle icon not tokenized**  
`component-classes.css` line 393: `font-size: 1.25rem` and line 401: `rotate(45deg)` are both hardcoded. Add `--accordion-toggle-size` and `--accordion-toggle-rotation`.

**MINOR — `:has()` card anatomy fallback**  
`component-classes.css` line 167 uses `:has()` to suppress double-padding when anatomy children are present. Older browsers (pre-Chrome 105, pre-Firefox 121) will render cards with doubled padding. Graceful but worth documenting.

### Missing components (not in backlog)

The current 20-item backlog captures most standard patterns. The following are genuinely absent:
- **Prose/article wrapper** — no `.prose` class for long-form body text (line-height, measure, list spacing)
- **Toggle/switch** — binary form control distinct from checkbox
- **Combobox / searchable select** — higher-value form pattern
- **File upload** — form staple
- **Toast / snackbar** — transient feedback (T-32 alert is for persistent inline feedback, not toasts)
- **Empty state** — no-results, zero-data pattern
- **Drawer / sheet** — slide-out overlay (T-40 is dialog, not drawer)
- **Skip-to-content link** — accessibility baseline
- **Stepper / progress bar** — form flows
- **Copy-to-clipboard enhancement** for T-33 code block

## Perspective 4 — Consumer Developer Experience

### npm package: mostly correct

`package.json` exports all 4 artifacts correctly:
- `.` → `farn.css`
- `./tokens` → `farn-tokens.css`
- `./components` → `farn-components.css`
- `./typography` → `farn-typography.css` ✓

Version `0.1.0` is consistent across `package.json` and `CHANGELOG.md`.

### Critical DX gaps

**CRITICAL — No llms.txt (T-45 still backlog)**  
An AI agent building a product with Farn must reverse-engineer the system from source. No machine-readable guide exists. The token naming scheme, artifact load order, and Tier-3 override pattern are invisible to LLM-based tooling. This is especially ironic given CLAUDE.md is otherwise an excellent agent guide.

**MAJOR — Getting Started doesn't explain Tier-3 override pattern**  
The Getting Started page shows how to reference tokens (`--color-accent`) but never explains how to retheme a component. The answer — "set `--btn-p-bg` in `:root` or scoped" — must be inferred from component documentation pages. No example shows:
```css
:root {
  --btn-p-bg: #my-brand-color;
  --btn-p-text: white;
}
```

**MAJOR — Import chain and artifact selection undocumented**  
Getting Started shows three import paths (default, `/tokens`, `/components`) but never explains:
- When to pick `farn.css` vs `farn-tokens.css`
- That `farn-components.css` must load *after* the token artifact (undefined tokens silently break components)
- That `farn-typography.css` exists at all (not mentioned in Getting Started or README)
- CDN paths for only 2 of 4 artifacts are shown

**MAJOR — README doesn't mention component classes or typography utilities**  
A new developer reading only the README learns Farn is a token system. The shipped component classes (`.btn`, `.card`, `.badge`, etc.) and typography utilities (`.text-display`, `.text-body`) are invisible. One sentence would fix this.

**MAJOR — Hardcoded CDN version strings**  
`getting-started.astro` (lines 35, 37, 41) and `README.md` (line 41) hardcode `@0.1.0`. These will drift from actual releases silently.

## Perspective 5 — CLAUDE.md Accuracy

Five of these will cause an agent to fail or produce incorrect output.

### Critical errors

**CRITICAL — "Adding a color token" step 4 references a deleted path**  
CLAUDE.md line 92:
```
4. Add to `site/src/pages/tokens/colors.astro`
```
This directory was removed in T-15 Phase 1b. The correct path is:
```
4. Add to `site/src/pages/styles/color.astro`
```

**CRITICAL — "Adding a component" Track B describes the pre-T-44 workflow**  
CLAUDE.md lines 104–108 instruct agents to:
1. Create `site/src/pages/components/<name>.astro`
2. Add to sidebar in `DocLayout.astro`

Both are wrong post-T-44. Individual component pages no longer exist (they were consolidated into 6 group pages). DocLayout has no editable sidebar — navigation is data-driven from `navigation.ts`. An agent following this workflow would create files that are never served.

**Correct workflow:**
1. Find the group page the component belongs to (layout / navigation / actions / forms / data / status)
2. Add an `<h2>` section with an accordion disclosure to `site/src/pages/components/<group>.astro`
3. No changes to DocLayout or nav structure needed for components within an existing group

**CRITICAL — No mention of `navigation.ts` as single source of truth**  
CLAUDE.md does not reference `site/src/data/navigation.ts`. An agent that needs to add a page to the nav will attempt to edit DocLayout directly, which won't work — DocLayout reads from `navigation.ts`.

**CRITICAL — No guidance for adding to an existing group page**  
The most common component task post-T-44 (adding a component section within a group page) is completely undocumented in CLAUDE.md.

### Major errors

**MAJOR — Complexity gate references "DocLayout sidebar"**  
CLAUDE.md line 131: "`DocLayout.astro` sidebar or URL structure changes" — the sidebar was removed in T-15. The correct gate should be: "`navigation.ts` structure changes or adding a new component group."

**MAJOR — Build guidance doesn't clarify the rebuild trigger or command shortcut**  
The build command is documented but there's no mention of `npm run build` as a shorthand, nor a clear statement that ALL FOUR artifacts must be rebuilt after any `tokens/` change (the dependency order matters — `farn-tokens.css` must be built before `farn.css`).

### Minor errors

**MINOR — Typography-classes.css design not explained**  
`tokens/typography-classes.css` is opt-in and NOT imported in `tokens/index.css` — it's only imported by DocLayout and built separately. CLAUDE.md documents the build step but doesn't explain the opt-in architecture or that agents should NOT add it to `tokens/index.css`.

**MINOR — Dogfood rule wording unclear**  
Line 72 says "every component shipped in dist/farn-components.css must also be imported by DocLayout.astro from tokens/component-classes.css." This is accurate but awkwardly worded — it means "test components on the docs site before shipping."

### Naming conventions table: passes

All prefix examples in the table match current `tokens/colors.css`. No stale or renamed tokens.

### Dark/light mode section: passes

The `base|layer|overlay` model and compose examples match the actual implementation in `tokens/dark-light.css`.

## Cross-Cutting Themes

### Theme 1: Focus-visible is the single most urgent fix
Two shipped interactive components (buttons, breadcrumbs) fail WCAG 2.1 Level A when `farn-components.css` is used standalone. This is a 5-minute fix with outsized impact on credibility. Do it before the next PR.

### Theme 2: The token architecture is structurally excellent but has execution gaps
The three-tier model (palette → semantic → component) is clean and well-understood. The gaps (hardcoded RGBA, badge fills, button spacing) are incremental execution failures, not architectural problems. They're fixable one token at a time.

### Theme 3: Documentation quality is high but skewed toward the system builders, not consumers
CLAUDE.md is detailed and thoughtful (when accurate). Component pages are excellent. But the Getting Started page — the first thing a consumer reads — doesn't teach the most important pattern (Tier-3 override). Fix Getting Started before the demo page.

### Theme 4: CLAUDE.md is the most urgent document to update
5 critical inaccuracies will cause AI agents (including future sessions of this agent) to create files in wrong locations, follow deprecated workflows, and miss the navigation.ts pattern entirely. This is a 2-hour fix with permanent compounding returns.

### Theme 5: The v1.0 milestone is 6 components away
Tables, alerts, code blocks, tabs, modals, and loading states are the only major blockers to a credible v1.0 claim. All are independently implementable with no cross-dependencies. A 6-week parallel sprint finishes them.
